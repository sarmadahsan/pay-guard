# BillGuard — Hackathon MVP Design

**Date:** 2026-10-17
**Event:** YC "Make Something Agents Want", overnight hackathon
**Priority:** proof of concept and a convincing live demo, not production
**Source spec:** `~/Downloads/writing-block (1).md` (BillGuard product spec)

## 1. Decisions made during brainstorming

| Decision | Choice | Why |
|---|---|---|
| Payment rail | Real x402 v2 on Base Sepolia for own sellers, plus one public Bazaar seller on Base mainnet | Strongest proof that sellers need no BillGuard integration |
| Stack | Python everywhere | Verified: `x402` 2.25.0 ships v2 headers, `x402HttpxClient`, FastAPI `payment_middleware`, `HTTPFacilitatorClient`, `EthAccountSigner`, client hooks |
| Buying agent | Claude Desktop / Claude Code over stdio | Zero agent code; satisfies "external agent client" criterion |
| Judge-facing visual | Tool outputs only; live ledger is a stretch (Supabase table view) | Time |
| Purchase flow | Explicit state machine, persisted before every network step | Signed payload must be on disk before send so timeouts are reconcilable |
| Durable store | Supabase Postgres via `supabase-py` | Table view doubles as the ledger; sponsor fit |
| Fallback | Local stub facilitator if Sepolia setup exceeds 2 hours | Demo must run regardless |

Sponsor fit (only where natural): **Supabase** as the store; **Armature** for the cold-start agent test after the server works; **Stripe** x402 preview as a second facilitator if access is obtained. Manufact, Blaxel, Inkbox: skip unless time is left.

## 2. Architecture

One Python monorepo managed with `uv`. Three processes: the MCP server, the demo sellers, and Claude Desktop.

```
pay-guard/
  billguard/
    server.py        # FastMCP stdio entrypoint; builds paid tools from registry
    registry.py      # allowlisted services (dataclasses)
    policy.py        # spending mandate loaded from policy.yaml (read-only to agent)
    purchase.py      # state machine (section 3)
    reconcile.py     # on-chain EIP-3009 authorizationState check
    verify.py        # deterministic validators
    store.py         # Supabase repository: purchases, evidence, findings
    wallet.py        # EthAccountSigner from env, per-network
  sellers/
    app.py           # FastAPI + official x402 payment_middleware; ZERO billguard imports
  scripts/
    setup_wallets.py # generate keys, print faucet links, check USDC balances
    smoke_sellers.py # pay each seller with the SDK auto-client, no BillGuard
    reset_demo.py    # wipe purchases/evidence/findings
  tests/
  policy.yaml
  docs/billguard/design/
```

Wallets: `BUYER_KEY_SEPOLIA` for demo sellers, `BUYER_KEY_MAINNET` (a few dollars USDC) for the Bazaar seller. Keys come from env, never logged, never stored as evidence. The registry pins each service to one network, so a Sepolia service can never be paid from the mainnet key.

Registry entry fields: `id`, `tool_name`, `description`, `method`, `url_template`, `input_schema`, `network` (CAIP-2), `accepted_price_minor` (USDC 6 decimals), `expected_content_type`, `validators` (list of names + params), `fulfillment_contract` (e.g. `{"pages": "$input.pages"}`).

Policy fields: `principal_id`, `total_budget_minor`, `per_purchase_cap_minor`, `allowed_networks`, `allowed_services`.

## 3. Purchase state machine

Purchase key: `(principal_id, purchase_intent_id, request_fingerprint)` where fingerprint = sha256 of service id + canonical JSON of arguments. Same intent, different arguments = different purchase.

Payment states, in order:

```
INTENT_RECORDED -> QUOTED -> AUTHORIZED | REJECTED
AUTHORIZED -> PAYLOAD_SIGNED -> SENT -> SETTLED | SETTLEMENT_UNKNOWN | PAYMENT_FAILED
```

Fulfillment state is a separate column: `PENDING | VERIFIED | FAILED | UNVERIFIED`.

Steps (each writes to the store before the next network call):

1. **Intent.** Upsert purchase row. If a row already exists for the key, return it (after reconciliation if `SETTLEMENT_UNKNOWN`). Never create a second payment for the same key.
2. **Quote.** Call the resource without payment. Expect 402 with `PAYMENT-REQUIRED`. Decode with the SDK. Store the full requirements as evidence `quote`. Select the `exact` scheme on the registry's network.
3. **Authorize.** Reject with `PRICE_MISMATCH` if `amount > accepted_price_minor`. Reject with `BUDGET_EXCEEDED` if over cap or remaining budget (budget = total minus all rows in `AUTHORIZED..SETTLED` plus `SETTLEMENT_UNKNOWN`, counted as spent). Store `authorization` evidence.
4. **Sign.** `x402Client.create_payment_payload(...)` with `ExactEvmScheme(EthAccountSigner)`. Store the payload (nonce, validBefore, payTo, amount, payer) as evidence `payment_payload`. State `PAYLOAD_SIGNED`.
5. **Send.** Retry the request with `PAYMENT-SIGNATURE` header, 15 s timeout. State `SENT`.
6. **Outcome.**
   - 2xx with `PAYMENT-RESPONSE`: decode settle response (`success`, `transaction`, `network`, `payer`, `amount`) → `SETTLED`, evidence `settlement`. Body → artifact evidence (content hash, size, content type, stored body or path).
   - 402 / 4xx with no settlement: `PAYMENT_FAILED`, evidence `seller_error`.
   - Timeout, connection error, or any exception after step 4: `SETTLEMENT_UNKNOWN`. Finding `SETTLEMENT_UNKNOWN`.
7. **Verify.** Run validators (section 5). Fulfillment state + findings.

Data model (Supabase):

- `purchases`: purchase_id, principal_id, task_id, purchase_intent_id, service_id, request_fingerprint, quoted_amount_minor, authorized_amount_minor, asset, network, pay_to, payment_status, fulfillment_status, settlement_tx, artifact_hash, created_at, updated_at
- `evidence`: evidence_id, purchase_id, kind, payload (jsonb), created_at
- `findings`: finding_id, purchase_id, code, severity (`proven` | `suspected`), summary, evidence_ids (jsonb array), safe_next_action, resolved_at

Finding codes: `PRICE_MISMATCH`, `BUDGET_EXCEEDED`, `SETTLEMENT_UNKNOWN`, `PAYMENT_FAILED`, `PAID_NO_DELIVERY`, `FULFILLMENT_FAILED`, `FULFILLMENT_UNVERIFIED`, `DUPLICATE_SUSPECTED`.

Money is always integer minor units (USDC, 6 decimals). No floats.

## 4. Demo sellers (all official x402 middleware, no BillGuard code)

One FastAPI app, `payment_middleware` with `HTTPFacilitatorClient("https://x402.org/facilitator")`, network `eip155:84532`, `pay_to` = seller wallet.

| Route | Price | Behavior | Staging |
|---|---|---|---|
| `GET /report/{ticker}` | $0.50 | JSON company record | none |
| `GET /research?topic=&stall=1` | $0.75 | JSON research result | after-settle hook sleeps 90 s when `stall=1`, so settlement completes before the client's 15 s timeout fires. Fallback: tiny proxy that forwards then drops the response. |
| `POST /convert` `{doc_id, pages}` | $2.00 | PDF built with pypdf | returns 12 pages regardless of `pages` |
| `GET /report-premium/{ticker}` | $0.75 | same as report | registry accepts $0.50 → `PRICE_MISMATCH` before signing |

Public seller: one cheap endpoint chosen from the CDP Bazaar discovery API (no key needed) during the night, registered with network `eip155:8453`, validators `non_empty` + `content_hash` only. Paid from the mainnet wallet.

Scenario B resolution: after reconciliation proves settlement and no artifact exists, BillGuard records `PAID_NO_DELIVERY`. A retry with the same intent returns the settled record and states that a new payment requires `force_new_payment=true` and still counts against budget. BillGuard never claims a refund.

## 5. Reconciliation and verification

**Reconciliation** (`reconcile.py`), for `SETTLEMENT_UNKNOWN` rows, triggered by `reconcile_purchase` or automatically on a repeated intent:

1. Read `payer`, `nonce`, `validBefore` from the stored `payment_payload` evidence.
2. Call `authorizationState(payer, nonce)` on the USDC contract for that network via web3.py over a public RPC (Base Sepolia: `https://sepolia.base.org`, USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e`).
3. `true` → `SETTLED`; evidence `chain_check` with block number. If no artifact → `PAID_NO_DELIVERY`.
   `false` and `now > validBefore` → `PAYMENT_FAILED`; safe to pay again.
   `false` and still valid → stays `SETTLEMENT_UNKNOWN`; response includes the deadline; new payment refused until then.
4. Stretch: find tx hash by scanning recent `Transfer(payer → payTo)` events.

Build-time check: confirm the SDK's exact scheme uses EIP-3009 for USDC on Sepolia (not Permit2). If Permit2, reconcile via the Permit2 nonce bitmap instead.

**Validators** (`verify.py`), each returns `(name, passed, detail)`:

- `json_schema(schema)`
- `field_equals(path, "$input.ticker")`
- `pdf_page_count("$input.pages")`
- `content_type(expected)`
- `non_empty`
- `content_hash` (always passes; stores sha256)

Any validator exception → `FULFILLMENT_UNVERIFIED`, never a pass. Every failed validator creates a `FULFILLMENT_FAILED` finding whose `evidence_ids` point at the validator result row and the artifact row.

**Error rules:**
- Any exception between `PAYLOAD_SIGNED` and a parsed settlement header → `SETTLEMENT_UNKNOWN`, never `PAYMENT_FAILED`.
- Store unreachable → fail before signing. No state, no money.
- 402 amount above registry price or mandate → reject before signing.
- Secrets never written to evidence.

## 6. MCP tool surface (FastMCP, stdio)

Paid tools, generated from the registry at startup, each with the service's input schema plus required `purchase_intent_id` and optional `task_id`, `force_new_payment`:

- `get_company_report`, `get_research_report`, `convert_document`, `<public_seller_tool>`

Response shape (spec §4): `purchase_id`, `payment_status`, `settled_amount`, `currency`, `network`, `settlement_tx`, `fulfillment_status`, `verification` (per-validator results), `findings`, `artifact` (inline JSON, or path/base64 for PDF), `safe_next_actions`.

Admin tools: `list_services`, `get_spending_policy`, `get_purchase(purchase_id)`, `list_findings(unresolved_only=true)`, `reconcile_purchase(purchase_id)`.

Tool descriptions are the only prompting the agent receives. They must say: reuse the same `purchase_intent_id` when retrying the same request; check `findings` before spending more.

## 7. Testing

- Pytest: sellers run in-process with a stub facilitator injected into the middleware; state machine tested against a local Supabase or a fake store implementing the same repository interface. One test per transition and per validator.
- Manual integration on Sepolia, one run per scenario, before the demo.
- `scripts/smoke_sellers.py` pays each seller with `x402HttpxClient` directly. Run it on stage to show sellers work without BillGuard.
- Cold-start test: fresh Claude session, the spec's research prompt, no hints about BillGuard internals. Optionally through Armature.

## 8. Overnight build order (checkpoint each)

1. Wallets, faucet USDC, seller A paid via SDK auto-client. **Checkpoint:** one real Sepolia settlement. Not done in 2 h → switch facilitator URL to a local stub, keep going.
2. Supabase schema, store, state machine, seller A through BillGuard in Claude Desktop over stdio. **Checkpoint:** Claude buys a report.
3. Mandate check, idempotency, seller D. **Checkpoint:** `PRICE_MISMATCH` rejection; repeated intent returns same record.
4. Seller C, pdf validator, findings. **Checkpoint:** `FULFILLMENT_FAILED` with evidence.
5. Seller B, reconciliation. **Checkpoint:** `SETTLEMENT_UNKNOWN` → `SETTLED` from chain → `PAID_NO_DELIVERY`; retry refused.
6. Public Bazaar seller on mainnet.
7. Stretch: Armature run, Supabase table view as live ledger, Stripe x402 seller, tx hash lookup.

Steps 3, 4, 5 are independent once step 2 lands and can be split across people.

## 9. Demo script (6 minutes)

1. Hook: "Agents can already spend money. Who checks they got what they paid for?"
2. Run `smoke_sellers.py`: sellers are ordinary x402 endpoints. Show `sellers/app.py` has no BillGuard import.
3. Claude Desktop, prompt from spec §8, budget $5.
4. Report purchase → `VERIFIED`, tx link on Sepolia explorer.
5. Research purchase → timeout → `SETTLEMENT_UNKNOWN`. Claude retries → BillGuard returns the existing record, reconciles on-chain → `SETTLED`, `PAID_NO_DELIVERY`, refuses silent second payment.
6. Convert purchase → 12 of 20 pages → `FULFILLMENT_FAILED` with page-count evidence.
7. `list_findings` → Claude summarizes spent, delivered, unresolved.
8. Public Bazaar seller on mainnet: "this seller has never heard of us."
9. Close with limits: no escrow, no refunds, schema-valid is not fact-checked.

## 10. Open risks

- Facilitator or Sepolia RPC flakiness during the demo → local stub facilitator switch, pre-recorded backup video.
- After-settle hook semantics in the SDK may differ → proxy fallback for scenario B.
- Permit2 vs EIP-3009 for USDC on Sepolia affects the reconcile query.
- Bazaar endpoint availability on the night; choose two candidates.
- Supabase latency adds ~100 ms per step; acceptable.
